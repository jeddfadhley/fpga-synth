# Roadmap — what needs to be done

Working plan for the synthesiser. Sequenced by **bring-up order**, which
deliberately differs from the signal-chain order in [CLAUDE.md](../CLAUDE.md):
we build the part that makes a verifiable sound first and defer MIDI parsing.

Each module is "done" only when it has a **self-checking cocotb testbench whose
expected values come from an independent Python model** — no eyeballing waveforms.

## Division of labour

- **You** write every synth RTL module (`rtl/*.v`) and must be able to explain
  every line.
- **Claude** writes the scaffolding: Python reference models (`model/`), cocotb
  testbench harnesses (`tb/`), the runner, toolchain, design notes, and reviews
  your RTL. Claude explains design trade-offs; it does not write the synth RTL.

Per-module workflow:

1. Agree the interface + fixed-point spec (design note in `docs/`).
2. Claude writes the Python model and the cocotb testbench to that spec.
3. You write the RTL to match.
4. Run `python3 sim/run.py <module>`, iterate until green.
5. Record results (utilisation, fmax) once synthesis is on the table.

## Phase 1 — NCO (numerically controlled oscillator)

The core tone generator: a phase accumulator that advances by `phase_inc` each
audio sample and indexes a sine wavetable in block RAM. Drive it with a
**hardcoded `phase_inc`** for now; MIDI supplies it later.

**What to build**
- `rtl/nco.v` — phase accumulator + wavetable lookup, registered output.
- `model/nco.py` — bit-accurate reference (same wavetable, same truncation).
- `tb/test_nco.py` — checks RTL samples against the model over many cycles and
  several frequencies, including at least one case that contradicts a design
  assumption (e.g. `phase_inc` that forces phase wrap mid-run, or the max
  representable frequency).

**Design decisions to pin first** (these go in a `docs/` design note):

| Decision | Options / trade-off | Suggested default |
|---|---|---|
| Phase accumulator width `ACC_W` | Wider = finer frequency resolution, negligible cost | 24 bits |
| Wavetable depth `TABLE_W` (address = top `TABLE_W` bits of phase) | More entries = smaller phase-truncation spurs, more BRAM | 10 bits (1024 entries) |
| Sample width `SAMPLE_W` | Wider = higher SNR, more BRAM/multiplier width | 16-bit signed |
| Output format | Document at the port | `S1.15` (signed, range [−1, 1)) |
| Update rate | Advance every `clk`, or once per audio-sample strobe | one advance per audio sample (see below) |

**Frequency relation** (with a sample-rate strobe at `F_S`):

```
phase_inc = round(f_out * 2**ACC_W / F_S)
f_out     = phase_inc * F_S / 2**ACC_W
```

Decide `F_S` (e.g. 48 kHz) and how it's derived from `clk` — likely a
sample-rate enable pulse generated by a divider. This choice defines the
fixed-point maths, so settle it before writing RTL.

**Open questions for you**
- Sine table generated at build time (Python emits a `$readmemh` file) or an
  `initial` block? Build-time generation keeps RTL and model using the *same*
  numbers — recommended.
- Full sine table, or exploit quarter-wave symmetry to cut BRAM 4×? Symmetry is
  a nice interview talking point but adds addressing logic; suggest full table
  first, optimise later.

**Acceptance**
- Output matches the Python model bit-for-bit across ≥3 frequencies for ≥1 full
  period each.
- A deliberately adversarial case (phase wrap / max frequency) passes.

## Phase 2 — Audio output

Turn the `S1.15` sample stream into something a speaker can play.

**What to build**
- `rtl/pwm_dac.v` or `rtl/sigma_delta.v` — 1-bit output into an external RC
  filter. Start with the simpler of the two.
- `model/` + `tb/` — check the modulator's average/duty against the input sample;
  for sigma-delta, check the error feedback keeps the running quantisation error
  bounded.

**Decisions:** PWM (simple, higher ripple, needs high carrier freq) vs
sigma-delta (better noise shaping, slightly more logic). I²S DAC is a later
option, not now.

**Acceptance:** modulator output, low-pass filtered in the model, reconstructs
the input sample within a stated error bound.

## Phase 3 — MIDI input

Now replace the hardcoded `phase_inc` with a real note source.

**What to build**
- `rtl/uart_rx.v` — 31250 baud, 8N1 receiver, oversampled; registered byte +
  strobe out.
- `rtl/midi_parse.v` — running-status-aware parser; emits note-on/note-off.
  **Note-on with velocity 0 is a note-off** — the testbench must cover it.
- `rtl/note_to_inc.v` — note number → `phase_inc` lookup (table generated in
  Python from the equal-tempered scale and `F_S`).
- Models + testbenches for each. UART TB feeds real MIDI byte streams; parser TB
  feeds malformed/edge streams (running status, velocity-0, note-off).

**Decisions:** UART oversampling factor (16× typical); how much of MIDI to
support (note-on/off is enough for monophonic; pitch bend / CC later).

**Acceptance:** a captured MIDI byte stream produces the correct sequence of
`phase_inc` values, velocity-0 handled as note-off.

## Phase 4 — ADSR envelope  → monophonic chain complete

**What to build**
- `rtl/adsr.v` — attack/decay/sustain/release state machine + a gain multiplier
  applied to the NCO output.
- `model/adsr.py` + `tb/test_adsr.py` — check the gain trajectory and every state
  transition, including note-off during attack (release from a partial level).

**Decisions:** linear vs exponential segments (exponential sounds better, costs a
multiply/shift per step); rate representation (increment per sample vs time
constant).

**Milestone:** MIDI → NCO → ADSR → audio out plays a single note end to end.
Record it working before touching polyphony.

## Phase 5 — Polyphony

The interview-worthy part: one voice engine **time-multiplexed** across N notes,
with a voice allocator handling note stealing.

**What to build**
- `rtl/voice_alloc.v` — maps incoming notes to voice slots; steals the
  oldest/quietest when full.
- Time-multiplexed datapath — the single NCO+ADSR processes N voices per audio
  sample; per-voice state (phase, envelope) lives in RAM.
- `rtl/mixer.v` — sum active voices with headroom / saturation.
- Models + testbenches, including the allocation policy under overload (more
  simultaneous notes than voices) and a saturation case in the mixer.

**Decisions:** voice count N (bounded by `clk / F_S / cycles-per-voice`);
allocation policy (oldest-note steal is simplest to justify); fixed-point
headroom in the mixer.

**Acceptance:** N-note chords render correctly; the (N+1)th note steals a voice
per the stated policy; mixer never wraps.

## Cross-cutting standards (from CLAUDE.md)

- Module per file, filename = module name. `snake_case` signals, `UPPER_CASE`
  parameters. Active-high synchronous `rst`; clock `clk`. Registered outputs at
  module boundaries.
- Every parameterised value is a `parameter` — no magic numbers.
- Fixed-point format documented in a comment at **every** port.
- Every testbench includes at least one case that contradicts a design
  assumption.
- Record for the README as they arrive: resource utilisation, fmax after
  synthesis, voice count, test coverage.

## Deferred / not yet decided

- Synthesis target hardware (Tang Nano 9K / iCE40 / Arty A7) — not bought;
  keep the design vendor-neutral, isolate any primitive behind a wrapper.
- GTKWave not installed (waveforms are debug-only; a pass never depends on them).
- I²S DAC (only if PWM/sigma-delta proves insufficient).
